# q5_latency.txt — HOW MUCH SENSOR PIPELINE LATENCY CAN THE ENVELOPE ABSORB?
# ~75 min, 3 cells. Run after q4_duration.
#
# THE GAP THIS CLOSES
#   The oracle publishes a centroid the instant the world moves. No camera
#   does. A real AR0234 pipeline spends time on exposure, readout, USB3
#   transfer and detection before the centroid is usable — call it 15-40 ms,
#   and more if the detector is not trivial. That time comes off tca directly,
#   and tca is the ONLY term the pooled fit says matters: P(save) = 0.5 at
#   0.810 s (95% CI 0.783-0.842), 10-90% transition width 0.169 s, over 125
#   on-course hover throws.
#
#   So a 60 ms pipeline is not a detail. It is ~35% of the transition band.
#
# WHY 23 m AND NOT 26 m
#   At 26 m the cell is at CEILING (10/10 twice), tca ~1.12 s, which is 0.31 s
#   clear of the LD50. Any latency below ~300 ms would be absorbed and the cell
#   would report 10/10 three times while measuring nothing. 23 m sits at tca
#   ~0.97 s and just measured 8/10, so there is room to fall and the fall is
#   readable. Same reasoning as q4: measure a lever where the curve is steep.
#
#   Predicted tca at 23 m, using the MEASURED 60 Hz dead time of 0.178 s
#   (not the old blended 0.177 constant, which the pooled analysis showed is
#   rate-dependent — 0.178 s at 60 Hz but 0.270 s at 12 Hz):
#       delay 0 ms  -> tca 0.972 s   P(save) ~ 0.95
#       delay 30 ms -> tca 0.942 s   P(save) ~ 0.93
#       delay 60 ms -> tca 0.912 s   P(save) ~ 0.90
#   That is a SHALLOW predicted decline, because 23 m still sits above the
#   knee. The honest expectation is therefore a small effect, and the cell is
#   as much a test of the delay model as of the aircraft.
#
# WHAT THE DELAY DOES AND DOES NOT MODEL
#   The centroid keeps its EXPOSURE timestamp and only ARRIVES late
#   (oracle.DelayLine). That is the charitable case: a well-engineered pipeline
#   timestamps at exposure, so the filter can predict forward across the delay
#   and lose no accuracy — it simply cannot act on data it does not have yet.
#   A pipeline that stamps at ARRIVAL would additionally bias the state
#   estimate, and would be a worse sensor than anything measured here. If these
#   cells show latency is cheap, that conclusion is conditional on exposure-
#   time stamping being a hardware requirement, and it should be written into
#   the hardware readiness package as one.
#
#   Release is quantised to Gazebo's 60 Hz pose grid, so an asked-for 0.030 s
#   is delivered as 0.030-0.047 s. Quantisation rounds AGAINST the sensor.
#
# CONTROL
#   lat00 is flown here rather than reusing st23's 8/10, because between-cell
#   escape offset in the pooled data spans x0.68 to x1.36 — a 2.0x spread. An
#   across-session control cannot referee a predicted 5% decline.
#
# PRE-REGISTERED PREDICTION
#   lat00 7-9 of 10. lat30 within 1 of lat00. lat60 within 2 of lat00, i.e.
#   6-9. A collapse at 60 ms would contradict the pooled fit and would mean
#   something other than tca is being disturbed — check track_updates and the
#   delivered rate before believing it.

TAG=lat00 RANGE=23.0 ORACLE_RATE=0.0 ORACLE_DELAY=0.0 DODGE_SPEED=3.0 RESP_OUT=1 CONFIG=$LAB/config/hz20_r23.0.yaml BATTERY_ARGS="-p hover_mode:=true" EXTRA_LAUNCH="oracle_params:=$LAB/params/oracle_stereo.yaml" EXPECT_BANNER="delay 0 ms"

TAG=lat30 RANGE=23.0 ORACLE_RATE=0.0 ORACLE_DELAY=0.030 DODGE_SPEED=3.0 RESP_OUT=1 CONFIG=$LAB/config/hz20_r23.0.yaml BATTERY_ARGS="-p hover_mode:=true" EXTRA_LAUNCH="oracle_params:=$LAB/params/oracle_stereo.yaml" EXPECT_BANNER="delay 30 ms"
