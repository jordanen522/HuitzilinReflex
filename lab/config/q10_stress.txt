# q10_stress.txt — THE LAST TWO AXES: BEARING PRECISION, AND EVERYTHING AT ONCE.
# ~15 min, 2 cells. Run last.
#
# WHY THESE TWO AND NOTHING ELSE
#   Going through the robustness axes one at a time, everything else is now
#   either flown or unanswerable in simulation:
#     speed          flown  ladder 20/26/28 m/s at 26 m
#     reach          flown  8/12/16/20/21/23/26 m
#     rate           flown  12 vs 60 Hz (delivered, after the pose-grid fix)
#     depth noise    flown  0.30 stereo vs 0.85 mono
#     latency        flown  0/30/60 ms
#     field of view  flown  45 vs 13.5 deg x 0/10/20 deg approach
#     aim offset     flown  the fd20 false-dodge geometry
#     trigger gate   flown  threat_radius_m 0.75 vs 1.25
#     BEARING NOISE  never swept -> bear10
#     INTERACTIONS   never tested at all -> stack
#     drone in motion   NOT ANSWERABLE HERE. Patrol cannot deliver a hit at
#                       range (0 of 98 throws inside 0.109 m), which is why the
#                       whole envelope is hover. This is a harness limit, not a
#                       result, and it belongs in the hardware package as a
#                       validation item rather than as another cell.
#     wind / lighting   no model exists in this sim. Inventing one would be
#                       simulating our own assumptions, not measuring anything.
#
# CELL 1 — bear10: CLOSE THE BEARING AXIS WITH ONE SHOT
#   Cross-range noise has been 0.02 m in every cell ever flown, inherited
#   unexamined. bear10 raises it to 0.10 m, which at 26 m and 0.300 mrad/px is
#   12.8 px — BIGGER THAN THE 11 px BALL. If the envelope survives a bearing
#   error larger than the target, bearing precision is not a spec driver and
#   the axis is closed in one cell. Only a failure would justify flying 0.05 m
#   to find the real boundary.
#   Bearing error feeds miss_m, and miss_m < threat_radius_m is the gate that
#   holds the dodge, so a cost should appear as a LATER COMMIT — read
#   track_age_s and tca_s, not only the save count.
#   PRE-REGISTERED: >= 8/10, track_age within 0.03 s of the 26 m reference.
#
# CELL 2 — stack: THE PRODUCT ACCEPTANCE CELL
#   Every other cell is one-factor-at-a-time. Hardware is not. stack sets the
#   real 13.5 deg cone, depth 0.30, bearing 0.05, latency 30 ms, the SHIPPED
#   dodge_speed 1.5, at the reference 26 m / 20 m/s / 60 Hz, head-on.
#   PRE-REGISTERED: >= 8/10, because commit tca at 26 m is ~1.12 s and that is
#   0.31 s clear of the 0.810 s LD50, more than the sum of the degradations.
#   A result below 8/10 is the informative one: it would mean the degradations
#   COMPOUND rather than add, and every single-factor null in the campaign
#   would need re-reading. Diagnose via track_age_s before anything else.
#
# Both are head-on and dead-centre, so score on the counterfactual as usual
# (saved = counterfactual_min_m <= 0.30 AND actual > 0.30), and check
# first_det_range_m ~= 26.

TAG=bear10 RANGE=26.0 ORACLE_RATE=0.0 DODGE_SPEED=1.5 RESP_OUT=1 CONFIG=$LAB/config/hz20_r26.0.yaml BATTERY_ARGS="-p hover_mode:=true" EXTRA_LAUNCH="oracle_params:=$LAB/params/oracle_stereo_bear10.yaml" EXPECT_BANNER="0.3, 0.1, 0.1"
